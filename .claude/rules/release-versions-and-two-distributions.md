# 이 레포는 배포판이 **둘**이다 — 번호는 «미청구»여야 한다

> 이 규칙이 여기 있는 이유: 배포판 파일을 여는 순간에만 참이다. `CLAUDE.md` §2 는
> 「태그가 두 종류이고 platform 이 핀으로 소비한다」를 말한다. 이 파일은 그 다음 —
> **번호를 고르는 순간에 무엇이 잘못될 수 있는가**를 말한다.

| 배포판 | 태그 | 버전이 사는 곳 |
|---|---|---|
| `fcc-test-contracts` (루트) | `v0.1.x` | `pyproject.toml` |
| `fcc-test-kernel` | `kernel-v0.x.y` | `packages/fcc-test-kernel/pyproject.toml` |

## 1. 번호를 올리기 전에 — 그 번호를 «누가 이미 가져갔는지» 물어라

**형제 세션이 같은 번호를 먼저 가져갈 수 있고, git 은 그것을 조용히 병합한다.**
실측 2026-09-05: 두 배송(PR #28·#29)이 각자 `0.1.18 → 0.1.19` 로 올렸다.
**같은 줄**을 썼으므로 병합 충돌이 나지 않았고 **아무 게이트도 붉지 않았다.**
먼저 머지된 쪽이 태그를 붙였고, 그 태그에는 나중 변경이 들어 있지 않다.
소비 레인이 그 번호로 핀하면 받는 것이 기대한 것이 아니며 —
**그 상태는 「핀이 맞다」와 같은 모양이다.**

봉인이 있다: `tests/test_release_version_is_unclaimed.py`.
그것이 묻는 것은 「태그가 있는가」가 아니라 **「그 태그가 이 배포판의 변경을 전부 담았는가」**다.

```bash
git log <tag>..HEAD -- <이 배포판의 트리>      # 비어 있어야 한다
```

⚠️ **이 게이트는 «커밋된 것»만 본다.** 배포되는 파일을 고쳐 놓고 아직 커밋하지 않은
상태는 초록이다. 판정은 첫 커밋 직후에 온다 — 「고쳤는데 안 붉네」를 게이트가 안 도는
것으로 읽지 마라.

## 2. 태그는 머지 «뒤에» 내고, 그 전에 사람에게 묻는다

`CLAUDE.md` §2 가 「태그 push 는 승인 지점」이라 적는다. 순서를 적어 둔다:

```
번호 미청구 확인 → 커밋 → PR → 머지 → 사람에게 승인 요청 → 태그 push → 소비 레인 핀
```

태그를 **옮기지 마라.** 이미 나간 번호를 다시 쓰면 소비 레인의 핀이 말없이 다른 것을 뜻하게 된다.

## 3. 커널로 «옮길» 때 — 그 배포판 안에 소비자가 있는가

실측 2026-09-07 (`7b81072`): `notification_types` 를 커널로 옮겼는데
**그 배포판 안에 소비자가 하나도 없었다.** 옮기는 것 자체는 옳아도, 소비자가
소비 레인에만 있으면 커널 시험은 그 이관을 검증하지 못한다.

> ### 🧭 스스로 묻는 질문
> **「내가 고른 번호를, 지금 열려 있는 다른 PR 이 쓰고 있지 않은가?」**
> 그리고 **「이 이관을 검증하는 시험이 «이 배포판 안»에 있는가?」**
